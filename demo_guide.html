專案簡介

外送大師是一款以 Python + Flask 實作的位置感知 Web 遊戲。 玩家在 60 秒內扮演外送員，接受顧客訂單、搜尋附近真實商家、計算實際步行路線， 並在地圖上觀看機車動畫完成外送。 整個流程串接兩個免費無金鑰的真實地圖 API。

核心亮點：全程使用真實地理資料（OpenStreetMap）； 地圖動畫、地點搜尋、路線計算全部源自正式 API，不使用任何假資料或硬編碼座標。

限速機制（Rate Limiting）

Nominatim 規定最多每秒 1 次請求，違規會被封 IP。

# 全 process 共享的限速鎖（geocoding.py:13-35）
_RATE_LOCK = threading.Lock()
_LAST_CALL = 0.0

def _search(self, params):
    global _LAST_CALL
    with _RATE_LOCK:              # 串行化：同一時間只有一個執行緒能送請求
        wait = config.API_DELAY - (time.time() - _LAST_CALL)
        if wait > 0:
            time.sleep(wait)       # 等夠 1.1 秒後才送
        _LAST_CALL = time.time()
        resp = requests.get(...)   # Lock 內送出，確保間隔
鎖必須是全 process 層級（module-level variable），因為每個 Flask request 都會 new Geocoder()，若鎖是 instance 屬性，背景 thread 和主 thread 各有一把，互不等待，仍會超速。

地點搜尋（search_venues）

使用 Nominatim 的 結構化參數（amenity=、shop=）而非純文字搜尋，精確度更高。

def game_seconds(self, osrm_duration_s):

Haversine 距離公式

def haversine(lat1, lon1, lat2, lon2):
    """地球球面直線距離（公尺）"""
    R = 6_371_000                      # 地球半徑（公尺）
    p1, p2 = math.radians(lat1), math.radians(lat2)
    dp = math.radians(lat2 - lat1)
    dl = math.radians(lon2 - lon1)
    a = math.sin(dp/2)**2 + math.cos(p1)*math.cos(p2)*math.sin(dl/2)**2
    return 2 * R * math.asin(math.sqrt(a))

隨機顧客座標生成

def _random_offset(lat, lon, min_m=400, max_m=1600):
    angle = random.uniform(0, 2 * math.pi)      # 隨機方向
    dist  = random.uniform(min_m, max_m)            # 400m~1600m 距離
    dlat  = (dist * math.cos(angle)) / 111_000
    dlon  = (dist * math.sin(angle)) / (111_000 * math.cos(math.radians(lat)))
    # 注意：dlon 要除以 cos(lat)，因為越靠近極點，1度經度對應的距離越短
    return lat + dlat, lon + dlon

路線座標簡化

def _simplify(route, max_pts=60):
    """OSRM 可能回傳數百個點，只取 60 個均勻採樣，減少 HTML 體積。"""
    n = len(route)
    if n <= max_pts: return route
    step = (n - 1) / (max_pts - 1)
    return [route[round(i * step)] for i in range(max_pts - 1)] + [route[-1]]

實作細節：機車動畫 (JavaScript)

動畫原理（時間線性插值）

// 核心：依時間進度在路線點之間線性插值
function render(now) {
  var prog = Math.min((now - t0) / durMs, 1);   // 0.0 → 1.0
  var pos  = prog * (route.length - 1);           // 在路線陣列中的位置
  var idx  = Math.floor(pos);
  var f    = pos - idx;                            // 小數部分（插值因子）
  marker.setLatLng([
    route[idx][0] + (route[idx+1][0] - route[idx][0]) * f,
    route[idx][1] + (route[idx+1][1] - route[idx][1]) * f,
  ]);
}

背景預取（Prefetch）

每次送達後，立刻啟動 Thread 預先搜尋下一個訂單的餐廳，讓玩家接單時無需等待：

# api_deliver() 完成後啟動預取
threading.Thread(
    target=_prefetch_venues,
    args=(gid, new_order["id"], tuple(g["player_pos"])),
    daemon=True,
).start()

def _prefetch_venues(game_id, order_id, player_pos):
    time.sleep(0.8)            # 避免與地圖重建撞在一起
    venues = geocoder.search_venues(...)
    with _games_lock:
        order["venues_prefetched"] = venues   # 存入 game state

# api_accept() 優先使用預取結果
if order.get("venues_prefetched"):
    venues = order.pop("venues_prefetched")  # 秒回應，跳過 API 呼叫
_games_lock 的使用：讀取不需要鎖（Python dict 讀取是原子的），寫入必須加鎖防止 race condition。預取函式在鎖內二次確認 order 沒被其他 thread 先填好，才寫入。

def _dedup_scores(scores):
    """同名玩家只保留最高分（dict 去重 + 降序排序）"""
    best = {}
    for s in scores:
        n = s["name"]
        if n not in best or s["money"] > best[n]["money"]:
            best[n] = s
    return sorted(best.values(), key=lambda x: x["money"], reverse=True)

def save_score(name, money, deliveries, city):
    scores = load_leaderboard()
    scores.append({...})
    scores = _dedup_scores(scores)[:config.LEADERBOARD_MAX]  # 最多 10 筆
    _write_leaderboard(scores)
    rank = next((i+1 for i, s in enumerate(scores)
                 if s["name"] == name and s["money"] == money), None)
    return rank, scores    # 回傳名次給 result.html 顯示

助教 QA — API 相關

為什麼 Nominatim 的 Rate Limiting 要用全域變數，而不是放在 Geocoder 的 instance 裡？

因為每個 Flask request 進來都會 new Geocoder()，背景 prefetch thread 也會建立自己的 Geocoder 實例。如果鎖是 instance 屬性，每個 instance 各有一把鎖，互不等待，實際上完全沒有限速效果。

必須用 module-level 的 _RATE_LOCK 和 _LAST_CALL，讓所有實例、所有 thread 都共享同一把鎖，確保整個 process 每 1.1 秒最多送一次 Nominatim 請求。

Nominatim 的 User-Agent 是什麼？為什麼一定要加？

Nominatim 的使用條款要求每個請求都帶有 User-Agent header，必須包含可聯絡的 email 或應用程式名稱。沒有 User-Agent 會收到 HTTP 403 Forbidden。

設定在 config.py 的 USER_AGENT，Geocoder 初始化時設為 self.headers = {"User-Agent": config.USER_AGENT}，每次 requests.get 都帶上這個 header。

OSRM 的座標順序為什麼跟 Folium 相反？你們是怎麼處理的？

OSRM 遵循 GeoJSON 標準，座標是 [經度, 緯度]（lon, lat）；Folium 跟大多數地圖函式庫一樣用 [緯度, 經度]（lat, lon）。

處理點：
1. URL 構建時手動交換：f"{start[1]},{start[0]};{end[1]},{end[0]}"（取 tuple 的 index 1 和 0）
2. 回傳的 geometry 座標同樣需要轉換：[[c[1], c[0]] for c in coordinates]

便利商店搜不到怎麼辦？Fallback 鏈是怎麼設計的？

OSM 對便利商店的標記不如餐廳完整（有些只標 amenity 而非 shop name）。設計了一個 fallback 鏈：先搜 7-Eleven，沒有結果再搜 全家、萊爾富，最後 fallback 到 supermarket。

程式邏輯是一個 for 迴圈，遇到有結果就 break，否則繼續下一個 query。這樣保證用戶在任何有人居住的地方都能找到至少一個取貨點。

search_venues 中的 viewbox 和 bounded 參數是什麼意思？

viewbox 定義一個矩形搜尋框（左上角、右下角的經緯度）；bounded=1 告訴 Nominatim 只回傳框內的結果（不加這個，Nominatim 可能把框外但匹配度高的結果排在前面）。

框的大小由 VENUE_SEARCH_RADIUS = 2000 公尺換算：1度緯度約 111km，所以 delta = 2000 / 111_000 ≈ 0.018 度，以玩家座標為中心做正方形包圍盒。

助教 QA — Flask 相關

為什麼要用 threading 而不是直接在 Flask route 裡做 geocode？

Nominatim 呼叫需要約 1-2 秒（加上限速等待）。如果直接在 /init route 裡同步執行，瀏覽器會卡在那裡等，體驗很差。

用 Thread 的好處：/init 立刻 redirect 到 /loading（幾乎 0 延遲），Loading 頁面輪詢 /api/loading_status（純 dict 讀取，快），Thread 在背景靜靜做完 geocode，完成後把 game state 改成 "ready"，前端偵測到就自動跳到遊戲畫面。

Flask session 在這裡是怎麼用的？每個玩家怎麼知道自己的遊戲是哪一局？

Flask session 是基於 cookie 的。/init 時生成一個 uuid4() 作為 game_id，存進 session（寫入 cookie）。之後每個 API 請求進來，get_game() 從 cookie 讀出 game_id，在 _games dict 查找對應的遊戲狀態。

這樣同一台電腦的不同分頁或不同使用者（不同 cookie）都有獨立的 game_id，資料不會混在一起。

_games_lock 是什麼？為什麼需要它？

Flask 設定 threaded=True（預設）時，每個 HTTP request 在不同的 thread 處理。同時，prefetch 和 loading 的背景 Thread 也在寫入 _games dict。

如果兩個 thread 同時寫入同一個 dict key，Python 雖然有 GIL（Global Interpreter Lock），但複合操作（讀-修改-寫）仍可能被中斷。threading.Lock() 確保同一時間只有一個 thread 能修改 _games，避免 race condition。

/api/state 這個 endpoint 的作用是什麼？為什麼要輪詢它？

/api/state 是前端與後端同步的橋樑，每 1.8 秒被呼叫一次，回傳：剩餘時間、當前 phase、金錢、可接訂單列表、當前訂單詳情、餐廳選項列表等。

選擇輪詢而非 WebSocket 的原因：實作簡單、Flask 原生支援、遊戲事件頻率低（不需要 sub-second 更新）。1.8 秒的間隔足夠在計時到 0 時及時跳結算頁。

助教 QA — 地圖相關

Folium 生成的 HTML 是怎麼顯示在頁面上的？為什麼用 iframe？

Folium 的 m.get_root().render() 回傳一個完整的 HTML 字串（含 Leaflet.js CDN、CSS、初始化 JavaScript）。這個字串存在 game state 的 map_html key 裡。

用 iframe 的原因：
1. Folium 生成的 HTML 有自己完整的 <html><head><body>，不能直接嵌入另一個頁面的 DOM
2. iframe 提供隔離的執行環境，Leaflet.js 的全域變數不會污染父頁面
3. 每次地圖需要更新（phase 改變），只需重設 iframe.src 即可

iframe 和父頁面怎麼溝通？為什麼可以點地圖上的餐廳標記讓右側卡片高亮？

透過 Web API：postMessage。地圖 HTML 裡注入的 JS 監聽 Leaflet marker 的 click 事件，點擊時呼叫 window.parent.postMessage({type:'marker_click', id: orderId}, '*')。

父頁面（game.html）有 window.addEventListener('message', e => {...})，收到後根據 e.data.id 找到對應的 [data-order-id] 元素並 scroll 高亮。這是唯一安全的跨 iframe 通訊方式。

地圖怎麼找到 Leaflet map 物件？findMap() 在做什麼？

Folium 會在 window 全域物件上建立一個形如 map_a1b2c3d4 的隨機變數名稱，每次生成都不一樣。

findMap() 掃描 window 的所有 key，用正規表示式 /^map_[a-f0-9]+$/ 找到符合的 key，再確認它有 addLayer 方法（是 Leaflet map 物件），回傳它。這樣就算 Folium 改變命名格式也能正確找到。

路線為什麼要做 _simplify()？OSRM 回傳的點不能直接用嗎？

OSRM 回傳的 GeoJSON 路線可能包含幾百個座標點（每個轉彎都有詳細幾何）。如果全部嵌進 HTML，字串會很大，影響地圖載入速度，動畫插值也需要遍歷更多點。

_simplify(route, max_pts=60) 用均勻採樣（step = (n-1)/(60-1)）從原始路線取 60 個代表點，最後一個點一定保留（確保終點精確）。視覺上幾乎看不出差異，但資料量大幅降低。

助教 QA — 遊戲邏輯

DEMO_SEED 是什麼？為什麼要固定亂數種子？

random.seed(42) 讓所有 random.* 呼叫產生固定序列。好處：每次 demo 訂單的位置、層級、品類都完全相同，不會因為亂數不好而遇到「所有訂單都超遠」或「全是普通單」的情況，讓展示更可控。

設為 None 就回到正常隨機模式（實際玩家遊玩時應設 None）。

訂單池（order_pool）的設計是什麼？每次接單後為什麼要生成新訂單？

遊戲開始時只生成 3 張初始訂單（MAX_VISIBLE_ORDERS = 3）。接單、略過、送達後，立刻生成一張新訂單補充，讓可接訂單維持在最多 3 張。

新訂單的顧客位置是以玩家當前位置為中心隨機生成的（fresh_order(tuple(g["player_pos"]))），而不是以起點。這確保遊戲越玩越往外跑，地圖中心也會跟著移動，體現「位置感知」的核心概念。

準時獎勵是怎麼計算和判斷的？

選定餐廳後（api_select_venue）：
1. 用 OSRM 算出兩段路線的秒數 t1（取餐）、t2（外送）
2. 用 game_seconds() 縮放成遊戲秒數
3. time_limit = int((t1 + t2) * tier["time_factor"])（普通 1.6 倍，急單 1.1 倍）
4. 記錄 active_selected_at = time.time()

送達時（api_deliver）：elapsed = time.time() - active_selected_at，若 elapsed <= time_limit 就發放 bonus（基本獎金的 30%）。

玩家送達後，自己的位置是怎麼更新的？

送達後（api_deliver）：g["player_pos"] = [order["customer_lat"], order["customer_lon"]]。玩家座標直接跳到顧客位置（即送達點），下一張訂單的顧客就以這個位置為中心隨機生成，模擬「送完就在那裡等下一單」的真實外送情境。

助教 QA — 進階設計

機車動畫為什麼要設計雙驅動（rAF + setInterval）？只用 rAF 不行嗎？

瀏覽器在背景分頁（使用者切到其他分頁）時，requestAnimationFrame 會被節流到約 1fps 甚至完全暫停，導致動畫永遠停在原地，也就無法發出 pickup_done / delivery_done 的 postMessage，遊戲卡死。

加入 setInterval(250ms) 作為備份：分頁切走時 rAF 停了，interval 繼續按時間推進座標插值。兩者都是時間驅動，結果完全一致，且 done flag 確保只有一個先到的 callback 觸發 finish()。

背景 prefetch 在做什麼？它如何改善使用者體驗？

送達後，新訂單被加入池中，此時立刻啟動 _prefetch_venues thread，偷偷 call Nominatim 搜尋那張訂單的餐廳。

玩家如果接了這張單，api_accept 先檢查 order["venues_prefetched"]，有的話直接用，省去一次 Nominatim 請求（約 1-2 秒）。接單幾乎瞬間顯示餐廳選單。

如果預取還沒完成（玩家接得太快），就 fallback 到正常的 Nominatim 查詢，不影響正確性。

DEMO 模式（⏸️）是如何在不損失時間的情況下暫停/恢復計時的？

遊戲的剩餘時間是用 time.time() - start_time 計算的（不是存一個計數器，而是存起始時間戳記）。

暫停時：記錄當下的剩餘秒數 paused_remaining = _remaining(g)，設 demo_mode = True，之後所有 _remaining() 呼叫直接回傳 paused_remaining（凍結）。

恢復時：把 start_time 重設為 now - (GAME_DURATION - paused_remaining)，讓時間公式繼續從剛才剩餘的秒數倒數，沒有損失任何時間。

為什麼地圖要放在 iframe 而不是直接用 Leaflet.js 在主頁面？

主要是配合 Folium 的工作方式：Folium 在 Python 端生成完整 HTML，包含自己的 <script> 標籤引入 Leaflet CDN 和初始化程式碼，無法乾淨地嵌入另一個已有 DOM 結構的頁面。

Iframe 的好處：每次更新只需換 src（加 ?timestamp 避免 cache），不需要手動銷毀和重建 Leaflet 地圖物件；JS 執行環境隔離，不怕 Leaflet 全域變數衝突。代價是每次 phase 切換都要重新載入地圖（約 0.5 秒），這是可接受的取捨。

這個 app 能支援多個玩家同時遊玩嗎？

設計上支援。每個玩家有獨立的 game_id（UUID）存在 cookie session，對應 _games dict 裡獨立的 entry。_games_lock 確保多個玩家同時寫入不會 race condition。

限制：_games 是 in-memory dict，重啟 Flask 就清空；沒有遊戲過期清除機制，長時間跑會佔記憶體。這在 demo/課程作業的規模完全可以接受，Production 環境會改用 Redis 等外部 store。

haversine 公式跟直接用畢氏定理算距離有什麼不同？為什麼要用 haversine？

畢氏定理假設平面座標系，但地球是球體。在台灣（緯度 ~25°），1 度經度對應的實際距離比 1 度緯度短（cos(25°) ≈ 0.906 倍），如果直接用 sqrt((dlat)² + (dlon)²) 會造成東西方向距離失真。

Haversine 公式考慮地球曲率，對台灣範圍（百公里內）誤差 < 0.5%，足以精確計算「玩家距顧客幾公尺」來排序餐廳列表和計算獎勵的距離加成。
